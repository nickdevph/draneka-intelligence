# Tank Analysis Skill Boundary

**Status:** PROPOSED / FOUNDER-AUTHORIZED BOUNDED DESIGN / RUNTIME NOT ACTIVATED  
**Date:** 2026-09-11

## Decision

Define a versioned `draneka-tank-analysis` skill package in `draneka-intelligence` as the canonical analysis-method contract for aquarium/tank questions that require deep Journal Assistant analysis.

This is a bounded design and implementation artifact. It does **not** activate or change the current production Journal Intelligence runtime.

## Responsibility split

```text
Journal Assistant
  owns user-facing intake and presentation
        ↓
Journal context/package builder
  selects bounded authoritative Tank/Journal context
        ↓
Draneka Intelligence
  owns intelligence request/execution lifecycle
        ↓
ChatGPT Work / admitted executor
  executes the analysis
        ↓
draneka-tank-analysis skill
  defines how tank questions must be reasoned about
        ↓
Tank analysis result schema
  defines the canonical machine-readable analysis result
        ↓
Journal Assistant inquiry/history
  presents result to the user without changing source-domain authority
```

## Ownership rules

- **Journal** remains authoritative for Tanks, livestock, tests, feeding, maintenance, observations, cases, schedules, and other Journal records.
- **Draneka Intelligence** owns intelligence execution lifecycle and result-envelope semantics.
- **The skill** owns neither source data nor execution state. It is a versioned reasoning/workflow contract.
- **ChatGPT Work/provider execution** is subordinate to Draneka contracts and is replaceable.
- **Draneka aquarium knowledge** is separate from the skill. Knowledge answers *what domain information is available*; the skill defines *how evidence must be analyzed*.

GitHub is the durable canonical source. A native ChatGPT Skill, API Skill, packaged worker asset, or other runtime representation should be generated or synchronized from this source rather than becoming a competing authority.

The package layout follows the Agent Skills convention: `SKILL.md` is required at the skill root, the skill `name` matches its parent directory, and supporting resources are referenced relative to that root.

## Versioning

- Skill versions use semantic versioning.
- The Draneka semantic version is stored in skill metadata and in every canonical result.
- OpenAI/platform skill-version identifiers may additionally exist at runtime but do not replace Draneka's semantic version.
- Breaking changes to result semantics require a new schema version.
- Historical results are not silently reinterpreted as though they were generated by a later skill version.

Initial proposed version:

```text
SKILL = draneka-tank-analysis@0.1.0
RESULT_SCHEMA = draneka.tank-analysis-result.v1
```

## Analysis principles

The skill must enforce:

1. tank-context-first reasoning;
2. current authoritative records before generic care ranges;
3. explicit separation of observed, derived, inferred, general-knowledge, and unknown information;
4. bounded hypothesis generation and evidence-based ranking;
5. transparent handling of stale, missing, and conflicting data;
6. conservative, proportional interventions;
7. explicit urgency, uncertainty, monitoring, and provenance;
8. no silent source-domain mutation.

## Integration boundary

No executor may be considered compliant merely because it receives `SKILL.md` as prompt text. Runtime integration should eventually prove that:

- the exact admitted skill version is resolved;
- the bounded context package is the intended revision;
- result output validates against the schema;
- execution provenance records the skill version used;
- stale or mismatched context/result submissions fail closed;
- the final result routes back to the correct inquiry/user/domain authority.

Those runtime changes are **not part of this initial skill-package change**.

## Explicit non-goals of this change

This package does not:

- migrate or alter production Journal Intelligence;
- change the current ChatGPT Work worker prompt or provider routing;
- change request/claim/result endpoints;
- change Supabase, Neon, GitHub append-only evidence custody, or other infrastructure;
- change Android behavior;
- admit new cross-domain producers;
- modify Journal records;
- define the complete Draneka aquarium knowledge base.
